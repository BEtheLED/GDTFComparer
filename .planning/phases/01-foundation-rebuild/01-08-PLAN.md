Gap closure for 01-REVIEW.md WR-01 (Warning): the app can no longer hang forever because of a file it cannot finish reading.
- Input side: picking a folder, named pipe or device file now gives an immediate friendly error. Before, the worker's open or read blocked indefinitely, the Run button stayed disabled, and the app had to be restarted.

## Phase Goal

Roadmap goal (verbatim; not user-story form, see Flagged Assumptions): Users can run the rebuilt app, pick a target and comparison `.gdtf` files, and get a correct, crash-free comparison in a modernized interface — replacing the old hand-rolled parser and tightly-coupled GUI end to end.

## Design notes (verified at planning time)

- On macOS, `os.open(path, os.O_RDONLY | os.O_NONBLOCK)` returned immediately for a FIFO with no writer and for a directory, and `stat.S_ISREG(os.fstat(fd).st_mode)` was False for both and True for a regular file. A plain `open(path, "rb")` on a FIFO blocks until a writer appears, which is the hang the review describes.
- `QThread.wait(10)` (int milliseconds) is accepted by the pinned PySide6 6.11.2 and returns a bool.
- A Python thread blocked in a kernel read cannot be stopped from Python. `QThread.terminate()` is unsafe with an interpreter running, and destroying a still-running `QThread` makes Qt abort the process. So the close path bounds the wait, lets the window close, and `app.main` ends the process with `os._exit` only when a worker is still running after the event loop has finished. The window stays referenced by `main()` until then, so no running `QThread` is ever destroyed.
