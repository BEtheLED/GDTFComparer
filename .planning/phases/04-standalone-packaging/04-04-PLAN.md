   - "Make a new release": (1) choose the next version (for example 0.1.1 for fixes or 0.2.0 for new features) and set `version` under `[project]` in pyproject.toml; commit. (2) `git push origin HEAD:main`. (3) `git tag -a v<version> -m "GDTF Comparer <version>"`, then `git push origin v<version>`. (4) Watch the "Build and release" run in the repository's Actions tab; it builds both apps, opens each one to check it, then publishes. (5) Open the Releases page and confirm both downloads are there. (6) Try the downloads by following README.md's "Download and run (no Python needed)" steps.

   - "If something goes wrong": a failed run publishes nothing (the release needs both builds and the version check). If a tag's run failed before any release was created, fix the problem, then delete the tag (`git push origin :refs/tags/v<version>` and `git tag -d v<version>`) and tag again. Once a release is published, never move or reuse its tag: delete the broken release on the Releases page if needed and publish a new patch version.
   - "Rules": never upload or replace release files by hand or from your own computer, only the files the run builds. The tag must equal "v" + pyproject.toml's version, or the run refuses to publish (this also stops GSD milestone tags from publishing). The workflow uses no secrets.

   - "Adding code signing later" (D-01 is reversible): on macOS, sign with an Apple Developer ID and notarize, after the PyInstaller step and before the ditto zip step in build-macos (needs the paid Apple Developer Program and repository secrets for the certificate). On Windows, sign GDTF Comparer.exe after the PyInstaller step and before Compress-Archive in build-windows (needs a code-signing certificate). Everything else in the pipeline stays the same (D-02). Signing would be the first and only reason to add secrets to the workflow.
