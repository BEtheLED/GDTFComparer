<objective>
Tracer slice for Phase 2: replace the hardcoded two-category display with a user-controlled attribute selection, wired end to end.

After this plan the comparison core stops throwing rows away. `compare()` returns rows for every category it is given. An always-visible "Attributes" side panel next to the results table lists those categories as collapsible sections, with one checkbox per attribute name. Checking and unchecking attributes decides which rows the table shows (ATTR-02). A search box narrows what the panel shows without changing what is compared (D-03). On first use only Beam and Physical Properties are checked, so the default table looks the same as it does today (D-04).

Purpose: ATTR-01 (browse the attribute set in a grouped picker) and ATTR-02 (choose which attributes are included). Plan 02-02 then fills the picker with the fixture's full 60+ attribute set. Plan 02-03 adds diff highlighting and the "show differences only" toggle on top of this proxy chain.
Output: `attribute_catalog()` and all-category `compare()` in core, a new `gui/attribute_picker.py`, `AttributeSelectionProxyModel` in `gui/table_model.py`, the splitter layout in `gui/main_window.py`, and the tests.
</objective>

## Phase Goal

**As a** lighting professional comparing fixtures, **I want to** browse and search the full GDTF attribute set, choose which attributes matter to me, and see which of those values differ, **so that** I am not limited to Beam and Physical Properties and can spot real differences at a glance.

(Story framing supplied by the plan-phase orchestrator. ROADMAP goal, verbatim: "Users can browse and filter the complete set of GDTF attributes and see which values differ, instead of being limited to two hardcoded categories.")

## Design notes (verified at planning time)

All checks used the shared venv (PySide6 6.11.2, qt-material 2.17) on the offscreen platform.

- **Selection unit is (category, attribute), not AttributeKey (Research Pattern 2, locked here as the reading of D-01/D-03).** A fixture with two beams has two BeamAngle rows but one BeamAngle checkbox. Checking it shows both rows. This is also the unit Phase 3 profiles will save (D-03 reversibility: costly).
- **Selection state model.** The picker keeps two sets: `_known` (every (category, attribute) pair it has ever listed) and `_checked`. When a catalog arrives, each pair not yet in `_known` is added to it, and is also added to `_checked` only if its category is in `DEFAULT_SELECTED_CATEGORIES` (D-04, by category membership as Research Open Question 2 recommends). Pairs already known keep the user's choice, including pairs missing from the current files, which get their old state back when those files return. This one rule covers first use, re-runs and changed file sets.
- **Proxy filtering through data roles.** Each proxy reads what it needs from `sourceModel().index(row, 0, parent).data(ROLE)`. It never calls `sourceModel().result()`, so it works at any position in the chain. Plan 02-03 inserts a differences-only proxy after this one. A Python tuple returned from a custom role comes back as a tuple through a QSortFilterProxyModel chain (verified).
- **Filter-change API.** In PySide6 6.11.2, `QSortFilterProxyModel`'s single-call invalidate methods raise DeprecationWarning. `beginFilterChange()` followed by `endFilterChange(QSortFilterProxyModel.Direction.Rows)` does not (verified). The whole suite passes today with `-W error::DeprecationWarning` (96 passed), so every verify command in this phase runs with that flag.
- **Coalesced signal.** Clicking a section checkbox makes Qt's `ItemIsAutoTristate` propagation fire `itemChanged` once per child plus once for the section. The picker records each leaf change synchronously, so `checked_attributes()` is always current. It emits `selection_changed` once per event-loop turn through a zero-interval single-shot QTimer, so a 30-attribute section click refilters the table once, not 30 times.
- **Window size.** With a 260 px side panel, the table viewport is 700 px at 1000 px window width and 980 px at 1280 px (measured in both themes). Phase 1's no-scrollbar tests in tests/gui/test_table_headers.py were tuned for a table about 980 px wide, so the default window becomes 1280x720.
- **Row order.** compare() used to sort by the index of the old two-category tuple, which would raise ValueError for any new category. It now ranks the categories in `LEADING_CATEGORIES` first, in that order, then every other category by first appearance across (target, *comparisons). The sort is stable, so row order within a category (first-seen) is unchanged from Phase 1.

<assumption_delta_decision>
Signal: derived to chosen ("choose which attributes are included in a comparison", ROADMAP Phase 2 success criterion 2).
Current anchor: the old two-category display tuple in core/models.py. It did two jobs: it was compare()'s hard row filter and it named the two categories that existed.
Decision: **promote**. The user's checked (category, attribute) set becomes the primary thing that decides which rows are shown. It is GUI-layer state held by AttributePicker, and core stays unaware of it. The old tuple is demoted and split into two single-purpose constants: `LEADING_CATEGORIES` (row-order anchor, keeps Phase 1 order) and `DEFAULT_SELECTED_CATEGORIES` (the D-04 first-use seed only). The old name is deleted rather than aliased, so every remaining use has to be revisited (Research Pitfall 2).
Rationale: keeping one constant in both roles would make any later change to the default selection silently reorder or filter core output.
</assumption_delta_decision>
