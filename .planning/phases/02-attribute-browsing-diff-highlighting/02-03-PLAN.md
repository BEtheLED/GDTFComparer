<objective>
Make differing values stand out in the results table, and let the user hide the rows that match, end to end.

compare() already computes a per-cell `ComparisonRow.differs` flag and a per-row `any_differs`, and Phase 1 never used them. This plan paints each differing comparison cell with a tint taken from the live qt-material theme (Phase 2 D-05). It adds a "Show differences only" checkbox above the table that hides the rows where every file agrees (Phase 2 D-06). The tint follows a live light/dark switch.

Purpose: DIFF-01, "The comparison table visually highlights which attribute values differ between the target and each comparison file" (ROADMAP Phase 2 success criterion 3).
Output: the highlight role, delegate and differences-only proxy in gui/table_model.py; theme-derived colour helpers in gui/theme.py; the checkbox, proxy-chain insertion and theme wiring in gui/main_window.py; two new GUI test files.
</objective>

## Plan Goal

**As a** lighting professional comparing a target fixture against one or more others, **I want** every value that differs from the target to stand out in the table, and a way to hide the rows where everything matches, **so that** I can spot the real differences at a glance without reading every row.

(ROADMAP Phase 2 goal, verbatim: "Users can browse and filter the complete set of GDTF attributes and see which values differ, instead of being limited to two hardcoded categories.")

## Design notes (verified at planning time)

Checks used the shared venv (PySide6 6.11.2, qt-material 2.17) on the offscreen platform, with `warnings.simplefilter("error", DeprecationWarning)`.

- **qt-material suppresses Qt's own BackgroundRole painting.** A QTableView cell whose model returns a translucent red BackgroundRole brush painted #ff9999 with no stylesheet. Once `theme.apply_theme` applied either qt-material theme, the same cell painted exactly like its unhighlighted neighbour (light #ffffff, dark #31363b). Adding `QTableView::item { background: transparent; }` did not help. The cause is qt-material's `QTableView::item` rule (padding, min-height, `border-color: transparent`), which makes Qt's stylesheet style draw the item itself and ignore the item's background brush. So a data()-level test alone would pass while the user sees nothing.
- **Fix, measured:** a QStyledItemDelegate subclass whose paint() fills option.rect with the index's BackgroundRole brush and then calls super().paint() renders the tint in both themes. At alpha 0.4 of primaryColor: light #a9c9ff against #ffffff (alternating rows #9cc1ff against #eaf2ff); dark #385789 against #31363b (alternating rows #3a5d95 against #333f4e). A selected row paints over it (#6aa2ff). This plan uses alpha 0.35 (DIFF_HIGHLIGHT_ALPHA) for text contrast; see flagged assumptions.
- **qt-material's own tints (material.qss.template):** alternating rows are primaryColor at 0.1, inactive selection is primaryColor at 0.2, and focused selection is solid primaryColor. The highlight uses a clearly stronger 0.35.
- **Proxy chain behaviour (measured):** a Python bool returned from a custom role arrives as a bool through QSortFilterProxyModel plus QIdentityProxyModel. `dataChanged(..., [BackgroundRole])` on the source model reaches the view with the filtered row count unchanged and the new brush visible. `beginFilterChange()` / `endFilterChange(QSortFilterProxyModel.Direction.Rows)` raise no DeprecationWarning (also verified by Plan 02-01).
- **qt_material.get_theme() is expensive.** It re-parses the theme XML from disk and writes os.environ on every call (RESEARCH Pattern 4). The colour is therefore looked up once per theme name through a functools.lru_cache and handed to the model as a ready QBrush. The model never looks up the theme, and data() only indexes a tuple.
- **Live switch ordering.** theme.OsThemeFollower re-themes the app on `styleHints().colorSchemeChanged`. MainWindow listens to the same signal, but maps the scheme with theme.theme_for_scheme itself instead of reading THEME_PROPERTY. The tint is then right whichever slot Qt runs first.
- **Decision labels.** theme.py's existing docstring cites Phase 1's D-05..D-08. New docstrings in this plan write "Phase 2 D-05" / "Phase 2 D-06" so the two decision sets are never confused.
